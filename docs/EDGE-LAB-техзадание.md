# EDGE LAB — Техническое задание

**Версия:** 1.0
**Тип:** платформа paper-trading для AI-анализа live-ставок на prediction-маркетах
**Референс UI:** файл `edge-lab-v18.jsx` (React-макет) — эталон интерфейса и поведения
**Стек-агностично:** документ описывает ЧТО и ПОЧЕМУ; конкретный стек выбирается при реализации

---

## 0. Что это и зачем

EDGE LAB — инструмент, где ИИ оценивает live-матчи (футбол, теннис), предлагает ставки на prediction-маркетах (Polymarket-стиль, цены в центах 0–100¢), и несколько стратегий параллельно управляют **виртуальными** деньгами. Цель — проверить на исторических и живых данных, находит ли ИИ реальный edge против рынка, и какая стратегия работает лучше.

**Ключевой принцип:** это симулятор (paper-trading). Реальные деньги не ставятся. Вся ценность — в аналитике: сравнить стратегии по ROI и метрикам качества (Brier, CLV, калибровка) и понять, реален ли эдж или это шум.

**Разделение двух интеллектов (критично для архитектуры):**
- **Аналитика** — оценивает матч объективно, НЕ знает про деньги. Один анализ на матч.
- **Стратегия** — читает анализ и решает денежные действия. Стратегий много, они сравниваются на одном и том же анализе.

Это разделение must-have: без него стратегии нельзя честно сравнить.

## 1. Иерархия сущностей

```
Спорт (football, tennis)
 └─ Турнир / Competition (ЧМ-2026, Лига чемпионов, ATP Masters…)
     └─ Матч (upcoming → lineup → live → finished)
         └─ Ставка / Позиция (по стратегии)
```

Параллельно:
```
Казна (глобальная, над всеми спортами)
 └─ Бюджет турнира ($)
     └─ Доля стратегии (%) → сумма в $
```

И отдельно:
```
Стратегия (принадлежит спорту)
Аналитический промт (базовый на спорт + переопределение на турнир)
Модель ИИ (выбирается на аналитику и на каждую стратегию отдельно)
```

**Статусы ставки (states):**
- `proposed` — стратегия предложила, ещё не исполнена

**Переоценка ≠ лог.** Лог — сухой журнал сделок. Переоценка — вербальное рассуждение «почему держим/фиксируем».

**Пробел триггеров переоценки (из аудита) закрыт полем trigger + правилом частоты:** переоценка запускается только по событию (гол, удаление, движение цены > порога, ключевая минута), НЕ по таймеру каждую секунду. Обязателен лимит: не чаще 1 переоценки на стратегию в N минут, чтобы не жечь токены и «комиссии».

### 2.14. quality_metrics (метрики качества стратегии)
Вычисляемое (можно materialized view или пересчёт по расписанию):
| поле | тип | описание |
|---|---|---|
| strategy_id | uuid FK | |
| samples | int | число рассчитанных матчей |
| brier | numeric | Brier score (ниже = лучше) |
| clv | numeric | closing line value, % |
| calibration | jsonb | массив {bucket, predicted, actual} |
| updated_at | timestamp | |

**Формулы:**
- **Brier** = среднее (ai_prob − outcome)², outcome ∈ {0,1}. Ниже — точнее вероятности.
- **CLV** = среднее (entry_price − closing_price) в пользу ставки. Положительный CLV = входил по цене лучше закрытия = ранний признак реального эджа.
- **Калибровка** = по корзинам предсказанной вероятности (50–60%, 60–70%…) сравнить предсказанную частоту с фактической.
- **Порог доверия:** метрики шумны до 20+ матчей — помечать «мало данных».

### 2.15. event_feed (глобальная лента — можно строить из событий)
Агрегируется из bets/reassessments/trade_log/matches по времени. Поля для отображения: t (время), type ('enter','reassess','settle','goal','lineup','skip'), sport, match, strategy, text, pnl. Может быть view поверх других таблиц, не обязательно отдельная таблица.

## 3. Ключевая бизнес-логика

### 3.1. Денежная модель (два уровня)
1. **Казна → турнир:** пользователь назначает бюджет турнира в $. Резервируется из свободного остатка казны. Инвариант: сумма бюджетов ≤ total_balance.
2. **Турнир → стратегии:** внутри бюджета турнира стратегии получают доли в % (ползунки, сумма ≤ 100). % × бюджет = $ стратегии.

Почему так: проверенной стратегии даёшь больше %, тестовой — меньше. При изменении бюджета турнира доли сохраняются, суммы пересчитываются. Свободный % не используется (не ошибка).

**Сравнение стратегий — по ROI (%), не по абсолюту.** Стратегия с $100 и +15% лучше, чем с $1000 и +4%.

### 3.2. Пороги: промт словами → числа кодом (КРИТИЧНО)
Стратегия описывается ЦЕЛЬНЫМ промтом на естественном языке (вход, размер, переоценка, выход, ограничители). Но **арифметику размеров ставок считает КОД, не LLM** — LLM ненадёжен в вычислениях.

Механика: движок парсит из промта числовые пороги в `params` (jsonb). Примеры извлекаемых порогов:
- `maxPerBet` — макс. доля бюджета на ставку (из «не более 20%»)
- `stop` — стоп-лосс портфеля (из «стоп −25%»)
- `minEdge` — мин. край для входа (из «edge ≥ 3%»)
- `flatSize` — фикс. размер (из «размер всегда 5%»)
- `kellyFraction`, `cap` — для Kelly-стратегий
- `tiers` — лесенка [[край, доля], …] (из «≥10% → 20%; 7–10% → 15%…»)
- `minConfidence` — мин. уверенность для входа

Пользователь видит и редактирует ОДИН промт. Пороги извлекаются под капотом и показываются человекочитаемо (напр. «макс. на ставку — 20%»). При реализации парсинг лучше делать структурированным вызовом LLM (extract to JSON) с последующей валидацией, а НЕ регэкспами.

### 3.3. Жизненный цикл матча и точки вызова ИИ
```
upcoming
  → [ИИ: pre-lineup оценка] когда матч скоро
lineup (состав вышел)
  → [ИИ: post-lineup оценка, приоритетная]
  → [для каждой стратегии: решение по ставкам на основе оценки]
live
  → [триггер-событие: гол/удаление/движение цены]
     → [ИИ: переоценка по стратегии] (с лимитом частоты)
     → возможен вход/выход/добавление позиции
  → [обновление котировок по расписанию/кнопке]
     → пересчёт mark-to-market открытых позиций
finished
  → [snapshot closing_price всех рынков — для CLV]
  → [settlement: каждая ставка won/lost, payout, P&L]
  → [пересчёт quality_metrics]
```

### 3.4. Settlement (расчёт)
При переходе в finished и получении финального счёта: для каждой открытой ставки определить исход рынка (won/lost), посчитать payout (для prediction-маркета: won → stake/entry_price_доля; lost → 0), зафиксировать closing_price для CLV, обновить equity стратегии.

### 3.5. Improvement (улучшение стратегии по данным)
Гейт: доступно только при samples ≥ 20 (иначе переобучение на шуме — показать прогресс «N/20» и вердикт «рано/можно»). При принятии: ИИ анализирует статистику, предлагает изменение промта (diff + обоснование), создаётся новая версия (version+1), старая — в strategy_versions. Возможен откат.

## 4. Экраны (UI-спека — детали см. в edge-lab-v18.jsx)

Навигация: горизонтальная полоса, 6 экранов. Казна (баланс/распределено/свободно) — над навигацией, видна всегда.

### 4.1. Матчи
- Вкладки спортов → плашки турниров (бюджет $ + прирост $ и ROI% + иконка «$» для бюджета).
- Кнопка «Распределить доли %» → модалка с ползунками стратегий.
- Полоса банков стратегий турнира (доля %, $, текущий equity, ROI%).
- Карточки матчей. Раскладка: слева табы+контент, справа ПОСТОЯННАЯ колонка котировок (центы, со скроллом, кнопка обновления ↻). На узком экране колонка уходит вниз, табы → дропдаун.
- **Вкладки матча:** Анализ / Ставки стратегий / Переоценки / Расчёт / Лог / Вывод.
  - **Анализ** (со скроллом, maxHeight): вертикальный поток ① до состава → ② после состава → ③ решения стратегий (обоснования словами). Тумблер кратко/подробно.
  - **Ставки стратегий:** чистые числа (рынок, edge, сумма, live-P&L, время входа). Мультиставки. На ПК — в 2 колонки.
  - **Переоценки:** по стратегиям, развёрнутые рассуждения по ходу, кнопка «Сделать переоценку» (live).
  - **Расчёт:** финальный счёт + тайминг (начало–конец, длительность, тип завершения), каждая ставка won/lost + payout.
  - **Лог:** сухой журнал по стратегиям.
  - **Вывод:** итог + урок для стратегии.
- Завершённый матч: правая колонка показывает итоги стратегий (P&L + ROI) вместо котировок.

### 4.2. Лента
Глобальная хронология всех событий по всем матчам/спортам. Фильтры (Входы/Переоценки/Расчёты/События матча/Пропуски). Пропуск («край недостаточен») — валидное событие дисциплины.

### 4.3. Портфель
Все ОТКРЫТЫЕ позиции по всем турнирам. Агрегаты: число позиций, экспозиция $, unrealized P&L, в плюсе/всего. Группировка по стратегии / по турниру.

### 4.4. Метрики
По каждой стратегии: Brier, CLV, вердикт («эдж реален/неясно/эджа нет»), график калибровки (предсказано vs факт по корзинам). Пометка «мало данных» при samples < 20. Блок-объяснение метрик.

### 4.5. Стратегии
- Блок аналитического промта: мастер-детейл (слева список Базовый/турниры, справа редактор), выбор модели, автосохранение с индикатором «сохранено ✓».
- Карточки стратегий: модель-бейдж, общая доходность (средний ROI по турнирам + P&L $), разворот с промтом, человекочитаемыми порогами, выбором модели, кнопками «Редактировать»/«Улучшить по данным».
- Создание/редактирование: название + кнопка «✨ придумать» (генерация 1–2 слов из промта через LLM), выбор модели, промт, кнопка «Распознать пороги», превью извлечённых порогов.

### 4.6. Модели
Провайдеры (Anthropic, OpenAI, Google), поле API-ключа (показать/скрыть/удалить), статус, список моделей. Модели доступны для выбора только при наличии ключа. **Ключи хранятся на бэкенде безопасно (env/secrets), НЕ в браузере, НЕ в БД в открытом виде.**

## 5. Внешние API (подключаются при реализации)

### 5.1. Prediction-маркет (Polymarket-стиль)
- **Назначение:** котировки рынков в центах, ликвидность, список рынков на матч.
- **Данные:** на матч десятки рынков (Team to Advance, O/U 0.5–5.5, BTTS, гандикапы, тайм-тоталы, extra time, пенальти). Цена в центах 0–100.
- **Частота:** обновление live по расписанию (напр. каждые N сек) + по кнопке. Обязателен snapshot цены закрытия для CLV.
- **На старте:** можно замокать реальными данными (в макете вшит пример Portugal vs Croatia, 34 рынка). Подключение API — следующим шагом через код.

### 5.2. Спортивные данные
- **Назначение:** расписание матчей, составы (флаг lineup_out), live-события (голы, удаления, минута), финальный счёт.
- **Триггерят:** переоценки (гол/удаление), смену state матча, settlement.

### 5.3. LLM-провайдеры
- **Anthropic / OpenAI / Google** — вызовы для: аналитики (оценка матча), решений стратегий, переоценок, генерации названия, извлечения порогов из промта, предложения улучшения.
- Модель выбирается отдельно на аналитику и на каждую стратегию.
- **Точки вызова** — см. 3.3. Обязательны: обработка ошибок (модель вернула невалидный JSON / API недоступен → status='failed', не ронять систему), таймауты, retry, лимит частоты переоценок.

## 6. Обработка ошибок и краевые случаи (не «счастливый путь»)

- **Оценка ИИ не удалась:** assessments.status='failed', UI показывает «оценка не удалась, повторить», матч не блокируется.
- **API котировок недоступен:** показать последний snapshot + метку устаревания, не падать.
- **Ставка не исполнена:** status='not_filled', видно в логе, не считается в P&L.
- **Финальный счёт не пришёл:** матч висит в live с меткой «ожидание результата», settlement откладывается.
- **Невалидный вывод LLM** (не JSON при извлечении порогов): повтор с уточнением или ручной ввод, не сохранять мусор.
- **Долгие события** (доп. время, пенальти): матч остаётся live, тайминг растёт, end_note фиксирует тип.

## 7. Рекомендуемый порядок реализации (для Claude Code)

**Не строить весь макет сразу.** Правильно — тонкий вертикальный срез на боевом стеке, потом наращивание:

**Этап 1 — фундамент данных:** БД по схеме §2 (со всеми статусами и полями CLV/версий сразу — их больно добавлять потом). Казна, турниры, доли, стратегии, матчи, ставки.

**Этап 2 — тонкий срез:** один спорт (футбол), один турнир, 1–2 стратегии, одна LLM, замоканные котировки. Прогнать ОДИН матч от pre-оценки до settlement. Ответить на главный вопрос: находит ли ИИ edge.

**Этап 3 — UI по макету:** воссоздать экраны из edge-lab-v18.jsx на реальных данных. Начать с экрана Матчи, затем Портфель/Метрики/Лента/Стратегии/Модели.

**Этап 4 — реальные API:** подключить Polymarket (котировки), спортивный API (события/счёт), остальные LLM-провайдеры. Включить триггеры переоценок и обновление котировок.

**Этап 5 — метрики и улучшение:** quality_metrics, калибровка/CLV на накопленных данных, improvement-цикл с версионированием.

## 8. Что сознательно НЕ входит (осознанные ограничения прототипа)

- Реальные деньги (это paper-trading — принципиально).
- Обучение весов модели (дообучаются ПРОМТЫ, не веса).
- Полноценный исторический бэктест (фокус на live; можно добавить позже).
- Мультипользовательность/аутентификация (одиночный инструмент на старте).
- Продакшн-грейд безопасность и масштабирование (закладывается схемой, но не оптимизируется преждевременно).

## 9. Инварианты (проверять всегда)

1. Свободный остаток казны ≥ 0.
2. Сумма долей стратегий по турниру ≤ 100%.
3. Сумма stake ставок стратегии на матче ≤ её бюджет на турнире.
4. Один pre + один post assessment на матч; post приоритетнее.
5. Аналитика не знает про деньги; стратегия читает аналитику.
6. Пороги размеров считает код, не LLM.
7. Переоценка только по триггеру, с лимитом частоты.
8. Метрики недостоверны при samples < 20 (помечать).
9. Ключи API не хранятся в браузере/открытом виде.
10. Сравнение стратегий — по ROI и метрикам качества, не по абсолютному P&L.
